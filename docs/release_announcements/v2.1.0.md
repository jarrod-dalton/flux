# flux v2.1.0

**Released:** 2026-08-30

flux v2.1.0 makes the decision and action system introduced in v2.0 safer,
clearer, and easier to audit. It also adds grouped decision points for cases
where one policy needs to answer several related questions together.

The irregular-time event engine remains the foundation. This release focuses
on making model behavior dependable when decisions, delayed actions, parameter
uncertainty, and parallel cohort simulation are layered onto that engine.

---

## Actions now have an explicit, durable lifecycle

A policy selection is not yet a realized action. An accepted `ActionEvent`
selection is staged as a pending event, competes on the entity timeline, and
changes state only if and when it is realized. Version 2.1 closes several gaps
in that lifecycle:

- a pending action now survives ordinary event-proposal refreshes;
- a realized action is retired instead of being selected repeatedly;
- multiple decision points can retain separate pending actions;
- `ActionEvent$decision_point_id` is enforced as provenance rather than treated
  as a routing override; and
- `DecisionPoint(on_pending_action = )` explicitly controls whether a new
  selection warns and replaces, silently replaces, keeps the earlier action, or
  stops with an error.

The 2.1 default is `"warn"`. A model that intentionally replaces an earlier
pending action can declare `on_pending_action = "replace"`, making that behavior
both quiet and explicit.

Decision callback failures also fail fast now. An error in a condition, policy,
grouped plan, or action handler is no longer converted into a valid-looking
veto, no-action choice, or successful no-effect action. Intentional condition
`FALSE`, ordinary-policy `NULL`, action-handler `NULL`, and explicit `NULL`
member selections inside a complete `DecisionPlan` remain supported.

Entity updates are safer as well: fluxCore constructs and validates the complete
candidate state, event, and history update before committing any of them. A
rejected update can no longer leave behind a phantom event or partially advanced
entity clock.

## Related decisions can share one policy consultation

Some events naturally raise several connected questions. In the urban delivery
tutorial, an incoming offer can require both a dispatch response and, when the
battery is low, a payload-safety decision.

`GroupedDecisionPoint()` lets a model declare that relationship. After the
group's trigger event updates the entity, fluxCore evaluates the member
conditions in declared order. If at least one member is eligible, the engine
calls `policy$propose_plan()` once with that eligible set. The returned
`DecisionPlan()` provides one action or explicit `NULL` choice for every
eligible member.

Core validates the whole plan before changing any pending-action slot. This is
an all-or-none boundary for accepting and staging the plan—not a promise that
the selected actions occur simultaneously. Each action that is staged retains
its own scheduled time and realizes independently on the event timeline.

Grouped trajectory records carry both the static group id and a deterministic
run-local activation id, so—together with `run_id`—analysts can reconstruct
which member decisions belonged to the same consultation.

## Cohort runs are more reproducible and easier to join

Version 2.1 tightens several contracts that become especially important in
large or parallel simulation studies:

- a complete schema and its model bundle must declare the same canonical model
  clock;
- `run_cohort(param_draws = ...)` and the `bundle$sample_params(D)` hook use a
  single typed `list<ParamContext>` boundary with stable, positive draw ids;
- cohort run ids now agree across the batch index, run list, callback
  `SimContext`, and trajectory records; and
- the outer execution layer owns random-number seeding, preventing a stored
  Engine seed from collapsing nominally distinct cohort or streaming
  replicates.

These are mostly hardening changes, but seeded results can change when an older
run was affected by the duplicate-seeding defect.

---

## The supporting packages move with Core

- **fluxForecast** adapts its public parameter-set interface to Core's typed
  draw boundary, preserves forecast-level seed ownership, and now surfaces Core
  run warnings instead of suppressing them.
- **fluxOrchestrate** requires constituent bundles to share one canonical model
  clock and aligns its parameter callbacks with typed contexts.
- **fluxModelTemplate** updates its direct callback examples and tests to the
  final Core 2.1 contracts.
- **fluxPrepare** and **fluxValidation** advance on the coordinated 2.1 release
  line without changing their public behavior.

---

## Upgrading from v2.0

Most ordinary v2.0 models continue to use the same high-level interfaces. Check
these deliberate contract changes:

1. Code reading `trajectory_table()$action_taken` must use
   `trajectory_table()$selected_action`. The new name accurately describes a
   policy selection; consult entity event history to establish realization.
2. Direct Core cohort parameter draws must be `ParamContext` objects. Bare
   parameter lists remain accepted by fluxForecast's public `param_sets`
   interface, which performs the adaptation at its boundary.
3. A full schema's `time_spec` must match the bundle's `time_spec`. A genuinely
   variables-only legacy schema still uses the bundle clock with a migration
   warning.
4. If repeated decisions intentionally supersede pending actions, set
   `on_pending_action = "replace"`; otherwise retain the default warning while
   reviewing the model's timing.
